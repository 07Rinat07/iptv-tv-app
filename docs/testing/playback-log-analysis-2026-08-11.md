# Анализ переключения и P2P-буфера — 11 августа 2026

Источник анализа: экспорт диагностики `myscanerIPTV-logs-1786447628621.txt` и три скриншота BlueStacks, сделанные между 16:08 и 16:22. В репозиторий журнал и скриншоты не добавляются, потому что это пользовательские диагностические артефакты.

## Подтверждённые наблюдения

В журнале 96 записей примерно за 22 минуты:

- 29 событий `player_play_request`;
- 6 подавленных дублирующих запросов;
- 6 успешных `embedded_ace_live_resolved`;
- 4 `embedded_ace_live_resolve_error` с внутренним timeout 60 секунд;
- 5 повторов одного `Invalid XMLTV format`;
- 4 EPG-отмены `StreamResetException: CANCEL`, записанные как ошибки;
- 0 событий с retained/readable buffer, producer/consumer rate, in-flight pieces или полезными peers.

Измеренное время от последнего запроса канала до результата:

| Результат | Каналы | Время |
|---|---:|---:|
| Успешная P2P-подготовка | 2977, 2980, 2982, 2983, 2987, 3048 | 21,2–47,3 с |
| Ошибка P2P-подготовки | 2970, 2981, 2984, 2988 | 75,9–87,2 с |

Сообщение `Timed out waiting for 60000 ms` описывает только внутреннюю стадию. Полный путь discovery/resolution/startup занимает ещё 16–27 секунд, поэтому пользователь ждёт заметно дольше заявленного timeout.

Для `sessionId=5` `player_ready` появился через 1,2, 21,6 и 29,1 секунды. Это похоже на повторные переходы BUFFERING → READY, но журнал не содержит отдельного события входа в buffering и не позволяет посчитать длительность rebuffer.

`app_trim_memory level=20` при 46 МБ из 256 МБ само по себе не подтверждает нехватку памяти или декодеров. По этому журналу главный блокер находится в lifecycle/transport/buffering, а не в доказанном decoder OOM.

## Что показывают скриншоты

1. Ошибка занимает большую часть видео и содержит длинную смесь русского текста с внутренним английским сообщением.
2. На двух скриншотах видео продолжает отображаться под ошибкой подготовки другого P2P-канала.
3. На третьем скриншоте одновременно видны badge `LibVLC` и ошибка встроенного Ace Live.
4. Название выбранного канала, активное видео, активный backend и ошибка последнего запроса не разделены визуально.

Это не доказывает, что внешний Ace Engine участвовал в P2P. Вероятнее, старый активный канал продолжает показываться, пока подготовка выбранного канала завершается ошибкой. UI должен явно различать `requestedChannel` и `activePlaybackSession`, иначе пользователь видит противоречивое состояние.

## План исправления

### P0. Единая модель переключения

1. Ввести неизменяемый `playbackRequestId` для каждого выбора и отдельный `playbackSessionId` только для реально запущенного media source.
2. Применять `latest request wins`: каждое async-событие resolution/start/error/ready обязано сверять request/session id до обновления UI и диагностики.
3. Сделать discovery, socket handshake, ожидание live-window и startup cooperative-cancellable; отменённый запрос завершать как `superseded`, а не как timeout/error.
4. Не удерживать общий mutex на время сетевого ожидания. Под lock разрешены только смена поколения, установка/снятие active runtime и короткая очистка ресурсов.
5. Явно выбрать UX при неудаче нового канала: либо остановить старое видео при начале переключения, либо оставить его и показать «Канал X не запущен, продолжает играть Y». Название и backend должны относиться к активной сессии.
6. Сбрасывать ошибку предыдущего request при новом выборе и не позволять старому callback вернуть её поверх новой/активной сессии.

### P0. Ограниченный startup budget

1. Логировать отдельные фазы `parse`, `catalog`, `DHT`, `tracker`, `connect`, `handshake`, `first_window`, `first_piece`, `startup_buffer`, `media_ready` с duration и итогом.
2. Ввести общий deadline поверх всех фаз, а не только 60 секунд вокруг `runtime.startup.await()`.
3. Завершать dead swarm раньше, если после ограниченного числа discovery cycles нет ни одного подключившегося/полезного peer.
4. Если peers и входящие pieces есть, показывать прогресс подготовки и использовать оставшийся общий budget; не перезапускать весь 60-секундный цикл без новых данных.
5. Первичная цель после измерений: dead swarm возвращает понятную ошибку не позднее 20 секунд, а p95 первого кадра рабочего Torrent TV канала на контрольной сети не превышает 30 секунд.

### P0. Непрерывная подкачка Ace Live

1. Добавить раз в 2–5 секунд безопасный snapshot: `retainedBytes`, `readableAheadBytes/seconds`, received/consumed bytes per second, useful/connected peers, in-flight chunks, current/head piece, recovery count и rebuffer duration.
2. Разделить startup low-water, steady-state target и high-water. Запросы должны продолжаться, пока запас не достиг high-water, и возобновляться до фактического голодания.
3. Управлять глубиной request pipeline по скорости producer/consumer и полезности peer, а не просто увеличивать общий размер памяти или число peers.
4. Проверить, что HTTP consumer не блокирует scheduler, непрочитанные данные не вытесняются скользящим окном, а освобождение старых bytes следует за подтверждённым чтением.
5. При падении ниже low-water запускать bounded refill/recovery; stall объявлять только когда буфер исчерпан и upstream действительно не продвигается.
6. Настраивать запас в секундах медиа по измеренному bitrate; при неизвестном bitrate использовать ограниченный byte fallback. Не считать фиксированные 4/16 МиБ универсальными для SD и HD.

### P1. EPG не должен мешать переключению

1. Валидировать XMLTV endpoint один раз на playlist и отрицательно кэшировать одинаковый parse failure с TTL, а не повторять его для каждого канала.
2. `CancellationException`, `StreamResetException: CANCEL` и отмену при смене канала считать ожидаемым `cancelled`, не пользовательской ошибкой.
3. Не связывать готовность видео с EPG; EPG обновляется независимо и не увеличивает playback startup budget.
4. В диагностике сохранить один агрегированный `epg_source_invalid` с URL без query/credentials и числом подавленных повторов.

### P1. Сообщения и состояние Player UI

1. Показывать короткий локализованный текст: «Канал не запустился: нет доступных peers» или «Истёк лимит подключения».
2. Техническую цепочку исключений оставлять в Diagnostics, а не перекрывать ею видео.
3. Badge `Media3`/`LibVLC`/`P2P` строить из active session, не из последнего выбранного канала или старого fallback state.
4. Для текущей подготовки показывать фазу и прошедшее время; дать пользователю немедленную отмену.
5. После успешного `READY` текущей сессии очищать только ошибку того же request/session, не ошибки диагностического журнала.

## Порядок реализации

1. Сначала telemetry и request/session correlation — без них нельзя доказать улучшение буфера.
2. Затем latest-request-wins и общий startup deadline.
3. После этого feedback-driven refill live-буфера.
4. Параллельно изолировать EPG negative cache/cancellation.
5. В конце упростить Player UI errors и выполнить регрессионную матрицу.
